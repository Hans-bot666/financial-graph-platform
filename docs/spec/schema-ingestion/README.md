## 3. 为什么要做（Why）

### 3.1 主诉求（产品一句话）

> **导入已有图数据，按选定 Schema 建成一张新图。** 这是本能力的最主要功能。

用户不是主要为了在 Nebula 里手写 DDL，也不是只想在已有空间里分析；他们要的是：

1. 手里已有数据（表、CSV、既有图导出、业务库抽取等）；
2. 有一套（或先建好一套）清晰的点边模型（Schema）；
3. 平台据此 **开出一张新图**，把清洗映射后的数据写进去，再拿去探索分析。

### 3.2 现状问题

1. **概念未产品化**  
   今天多靠脚本：`CREATE SPACE` + `schema.ngql` + 生成/导入数据。用户要自己理解「先 Space 再 Schema 再数据」，容易和「先建模再建图」的业务语言打架。

2. **Schema 与图实例脱节**  
   模型构建页、数据接入页多为前端本地 Demo；发布版本不会可靠落到 Nebula，也不会自动登记到「可分析图目录」。

3. **已有数据进不来主路径**  
   随机图脚本能造数，但「拿已有业务数据 → 选 Schema → 出新图」没有统一流水线；清洗映射与建图、注册、分析是断开的。

4. **与已完成的图空间选择不闭环**  
   探索分析已能选图数据库中的 Graph（黑名单除外），但 **新图从哪来** 仍靠运维手工建图。主功能应能在创建成功后进入可分析目录（创建后 `SHOW GRAPHS` 即可见，无需再改白名单）。

### 3.3 要解决的核心矛盾

> 业务语言是「先模型、再灌已有数据、得到新图」；引擎现实是「先 Space、再 Schema、再 INSERT」。

平台必须做适配层：对用户暴露「Schema 模板 + 导入建图」；对 Nebula 执行「建 Space → 应用已发布 Schema → 按映射写入 → 注册图实例」。

### 3.4 本期目标

1. 明确主路径：已有数据 + 已发布 Schema → 创建新图实例并导入。  
2. 明确 Schema 最小生命周期：草稿 → 校验 → 发布（不可变版本），导入只能绑已发布版本。  
3. 明确图实例与 Schema 版本的绑定关系（禁止漂移的「latest」）。  
4. 明确导入前门禁：类型、VID、主键、边端点等（与既有 `schema-and-ingestion-design.md` 对齐）。  
5. 创建成功的图可进入探索分析可选范围（与图空间选择规格衔接）。

### 3.5 本期不做（Non-goals）

- 浏览器直连 Nebula 做 DDL/导入。  
- 完整多数据源连接器矩阵（先 CSV/JSON 或平台已支持的本地上传即可作为 MVP）。  
- Schema 在线热迁移、复杂兼容矩阵全自动（破坏性变更走新主版本即可）。  
- per-space 细粒度 RBAC（沿用现有登录权限；空间级授权后续）。  
- 用全图 `COUNT` 作为导入成功的唯一验收（可用抽样对账 + 任务计数）。

### 3.6 设计原则

| 原则 | 说明 |
| --- | --- |
| 主路径优先 | 一切能力服务于「已有数据 → Schema → 新图」 |
| 模板与实例分离 | Schema 版本可复用；每张图是一次落地实例 |
| 版本钉死 | 映射与图实例绑定 `schema_id + version_id` |
| 后端为权威 | DDL、导入、登记只由 FastAPI 执行 |
| 先门禁再写入 | 预检失败不得创建半成品图或留下不可解释状态 |
| 与分析闭环 | 新图创建后应可被图空间目录发现并查询 |

## 4. 概念模型

```text
Schema 定义（可编辑草稿）
    │ 发布
    ▼
Schema 版本（不可变快照）──── 可被多个建图任务复用
    │
    │ 导入已有数据 + 字段映射
    ▼
图实例 GraphInstance  ←→  Nebula Space（一套已应用的 Schema + 数据）
    │
    ▼
探索分析（选 space 查询）
```

| 用户说法 | 平台对象 | Nebula |
| --- | --- | --- |
| 模型 / Schema | `schema_definition` + `schema_version` | Tag/Edge 定义（应用后） |
| 一张新图 | `graph_instance` | 一个 Space |
| 已有数据 | `data_source` / 上传文件 + `mapping` | 无（写入前） |
| 导入任务 | `ingestion_run` | INSERT 批次 |

## 6. 成功标准（摘要）

1. 用户可发布至少一个 Schema 版本。  
2. 用户可上传/选择已有数据，绑定该版本，完成映射与预检。  
3. 确认后平台创建 **新** 图空间、应用该 Schema、导入数据，并登记图实例。  
4. 探索分析中可选中该图并完成点查（不依赖手工改代码）。  
5. 预检失败或 DDL 失败时有明确错误，不静默落到 Mock，不假装导入成功。

详细需求见各 `.spec.md`。
