# 金融企业级图谱平台融合与交付计划

## 1. 结论

建议采用“前端融合、后端演进、数据分层”的路线：

- 以 `app-b8baqvzddgxt` 的 React + TypeScript + AntV G6 项目作为统一平台前端基座。
- 将当前反欺诈项目中的资金穿透、担保圈、失联客户等能力迁入统一前端的“探索分析 / 场景应用”模块。
- 保留 FastAPI + NebulaGraph 作为图查询与分析服务起点，但重构为受控的平台 API，禁止浏览器直接执行任意写入型 nGQL。
- 引入关系型元数据库保存租户、用户、角色、图空间目录、Schema 版本、查询模板、场景、子图、任务、审批与审计记录。Supabase/PostgreSQL 可用于试点，但必须由后端访问并实施细粒度权限策略。
- 数据接入、特征工厂和 Workflow 不应继续作为静态占位页，应按可独立验收的服务逐期交付。

不建议把当前原生 HTML/Canvas 前端继续扩展为企业级门户，也不建议把 Demo 直接连接生产 NebulaGraph 或继续使用匿名 Supabase 全开放策略。

## 3. 企业级能力缺口

### 3.1 P0：上线阻断项

1. 身份与权限
   - 当前 FastAPI 无认证、无 RBAC/ABAC、无租户和机构隔离。
   - Demo 的鉴权上下文未接入应用，类型引用不完整。
   - Supabase RLS 采用匿名全读写策略，不符合金融数据访问要求。

2. 查询安全
   - `/api/query` 可执行任意 nGQL，未区分只读/写入、无超时、行数和资源配额。
   - CORS 全开放；数据库账号、图空间和查询权限未按用户或机构隔离。
   - 缺少查询审批、敏感属性脱敏、导出控制和完整审计。

3. 数据真实性与一致性
   - 当前前后端混用 Mock、固定统计和固定结论。
   - 部分查询使用错误的 Tag 属性语法或与 Schema 不一致的边类型。
   - Schema、索引、Seed 缺少可重复迁移、就绪等待和回滚机制。

4. 可用性与工程质量
   - 两项目均缺少系统化自动测试。
   - 当前后端是单文件路由和全局连接单例，没有统一异常模型、重试、熔断和健康分层。
   - 缺少日志关联 ID、指标、追踪、告警、备份恢复和容量基线。

### 3.2 P1：试点必需项

- 图空间与 Schema 目录、版本、发布审批、影响分析和迁移任务。
- 数据源、字段映射、质量规则、批量导入、增量同步、失败重跑和血缘。
- 探索分析的搜索、扩展、筛选、路径、最短路、邻居、布局、聚合、快照与分享。
- 场景模板参数化、执行记录、证据链、风险结论、案件协作和导出水印。
- 多机构/多部门隔离、数据分级分类、字段级脱敏和操作审计。
- 高可用部署、容量压测、灾备演练和运维手册。

### 3.3 P2：规模化能力

- 图算法/特征工厂、离线与在线特征服务、特征版本和漂移监测。
- 可视化 DAG、任务调度、依赖、补数、重跑、告警与 SLA。
- 场景规则/模型版本、灰度发布、效果评估、反馈闭环。
- 多图空间、多环境、多机构模板复制和统一运营看板。

```text
  ├─ Metadata API（场景、子图、Schema、模板、收藏）
  ├─ Ingestion API（数据源、映射、校验、任务）
  └─ Job API（异步任务、状态、日志、重跑）
            │
  ┌─────────┴──────────┐
NebulaGraph          PostgreSQL
业务图数据            平台元数据/权限/审计
            │
对象存储 + 消息队列 + 调度器
导入文件/导出物/任务解耦
```

部署建议：开发环境继续使用 Docker Compose；试点和生产环境采用 Kubernetes 或机构认可的容器平台，NebulaGraph 至少 3 Meta + 3 Storage + 2 Graph，并基于实际容量进行副本、磁盘和备份设计。

## 5. 图谱分析界面融合设计

### 5.1 统一工作台布局

- 左侧：图空间、实体/关系类型、保存查询、场景模板、历史记录。
- 中间：G6 主画布，支持缩放、框选、套索、展开/收起、固定、布局切换和时间过滤。
- 右侧：节点/边详情、关联摘要、风险信号、数据来源、证据与操作审计。
- 底部：查询编辑器、可视化查询构建器、结果表格、执行计划、告警与任务日志。
- 顶部：机构/图空间切换、全局搜索、保存子图、加入场景、导出、分享和权限状态。

### 5.2 当前反欺诈能力的融合方式

- 将贷款回流、洗钱路径、虚增流水、垒大户、担保圈、派系、失联客户做成“场景模板”。
- 每个模板包含：版本、参数 Schema、只读查询/算法引用、结果映射、风险指标、证据说明、权限、超时和最大返回规模。
- 场景执行结果统一返回 `GraphResult`：`nodes`、`edges`、`columns`、`summary`、`warnings`、`traceId`、`executionTimeMs`、`truncated`。
- 场景结果可以继续探索、保存为子图、加入看板、创建案件或导出；所有操作记录审计。

### 5.3 API 契约原则

- 前端不拼接 nGQL，不直接访问 NebulaGraph 或 Supabase。
- 自由查询默认只读，并通过解析器拒绝 DDL/DML/用户管理语句；写操作进入 Schema/数据任务专用 API 和审批流。
- 节点和边使用统一结构，兼容 G6：边字段统一为 `source/target`，后端适配 Nebula 的 `src/dst`。
- 所有列表支持游标分页；所有图查询有节点/边数量上限、执行超时和取消机制。
- 错误使用稳定业务码，不向前端泄漏数据库堆栈或连接信息。

## 6. 分阶段开发计划

假设配置 1 名产品/领域负责人、1 名架构师、2 名前端、3 名后端/数据工程师、2 名测试、0.5 名 DevOps/安全，建议 20 周完成生产候选版。若团队不足，应保持阶段顺序并相应延长，不压缩安全和测试门禁。

### Phase 0：基线与架构护栏（第 1–2 周）

工作包：

- 建立统一仓库或清晰的前后端多仓策略、分支规范和 ADR。
- 固化 OpenAPI、GraphResult、错误码、字段命名和版本策略。
- 建立配置分层、密钥管理、数据库迁移、开发 Compose 和种子数据。
- 为现有接口补回归测试，清除线上路径中的静默 Mock。
- 完成威胁建模、数据分类分级和审计事件清单。

验收：CI 可重复构建；本地一键启动；核心三个场景有真实数据库回归；Mock 仅在显式测试配置启用；架构与安全基线评审通过。

### Phase 1：统一探索分析 MVP（第 3–6 周）

工作包：

- 将 Demo 前端迁入正式工程，建立 API Client、状态管理、错误边界和路由权限。
- G6 画布接入真实 Graph Query API，完成类型映射、布局、详情、筛选、扩展和结果表。
- 将现有反欺诈接口改造成版本化场景模板并接入统一工作台。
- 场景/子图/收藏/查询历史改由 Metadata API 持久化。
- 首页统计改为真实聚合，不再使用固定值。

验收：用户可选择图空间，执行受控查询和三个核心场景，在画布查看证据、保存并恢复子图；浏览器无直接数据库凭证；前端无 Mock 回退。

### Phase 2：身份、安全与治理（第 5–9 周，与 Phase 1 后半并行）

工作包：

- 对接机构 IdP（OIDC/SAML）、用户/机构/部门/角色模型。
- 实现图空间、场景、查询、导出、Schema、数据源的 RBAC + 数据范围控制。
- 查询白名单/AST 校验、超时、限流、配额、敏感字段脱敏和导出水印。
- 全链路审计、traceId、不可抵赖操作记录和审计检索。
- TLS、密钥轮换、依赖/SAST/镜像扫描和安全响应流程。

验收：越权、注入、匿名访问和跨机构访问测试全部阻断；高风险操作有审批/审计；安全评审无未关闭的严重或高危问题。

### Phase 3：模型构建与数据接入（第 8–13 周）

工作包：

- 模型构建器接入 Schema API；完成草稿、差异、校验、审批、发布、回滚和影响分析。
- 建立 CSV/JSON 首批数据接入，支持字段映射、主键、类型转换、去重和质量规则。
- 建立异步 Job API、任务队列、进度、日志、失败记录、幂等、断点续跑和重跑。
- 增加数据血缘、批次、来源和质量报告。

验收：可从空图空间设计并发布 Schema，导入标准测试数据，错误行可定位和重跑；重复执行不产生非预期重复数据；Schema 失败可回滚。

### Phase 4：场景运营、特征与 Workflow 基础（第 12–17 周）

工作包：

- 场景模板管理、参数配置、版本、灰度、执行历史和效果指标。
- 案件/线索状态、备注、证据快照和协作流转。
- 首批图特征：度、PageRank、社区、路径/环特征；离线任务优先。
- Workflow MVP：DAG、定时任务、依赖、失败重跑、通知。

验收：反欺诈场景可配置、发布、追踪和回放；至少 3 类图特征可产出并被场景消费；端到端任务链可监控与重跑。

### Phase 5：生产加固与试点验收（第 18–20 周）

工作包：

- 容量模型、基准压测、稳定性、故障注入、备份恢复和灾备演练。
- 可观测性仪表盘、SLO、告警、值班手册和应急预案。
- 数据迁移演练、权限复核、UAT、培训和上线回退方案。
- 试点机构灰度上线与两周稳定性观察。

验收：全部发布门禁通过；RTO/RPO 达标；连续稳定运行；关键用户 UAT 签字；回退演练成功。

### 7.2 P0 端到端测试用例

1. 用户经机构 IdP 登录，只能看到授权图空间和场景。
2. 按企业名称检索并执行贷款回流，返回预期节点、边、金额和证据链。
3. 执行担保圈，识别固定黄金数据中的完整闭环，不多报、不漏报。
4. 从场景结果展开节点、应用筛选、切换布局并查看原始属性与来源。
5. 保存子图到场景看板，退出重新登录后可恢复，其他机构不可读取。
6. 提交非法、写入型、超时和超规模查询，系统拒绝或截断并留下审计记录。
7. 创建 Schema 草稿、校验、审批、发布；失败迁移自动回滚。
8. 上传包含正确行、重复行、类型错误行和非法行的数据，结果与质量报告一致。
9. 导出敏感结果时触发权限检查、水印和审计；无权限用户被拒绝。
10. Graph 节点故障时请求可重试或明确失败，不返回 Mock 结果冒充真实数据。

### 7.3 初始性能基线（需在需求澄清后校准）

- 普通实体搜索：P95 ≤ 1 秒。
- 两跳邻居查询（结果 ≤ 500 节点）：P95 ≤ 3 秒。
- 场景查询（结果 ≤ 2,000 元素）：P95 ≤ 8 秒，超时可取消。
- 画布 1,000 节点保持可交互；超过阈值默认聚合或分页，不直接全量渲染。
- 首期目标并发：100 活跃用户、30 并发图查询；按试点真实规模压测后调整。
- 批量导入吞吐、RPO/RTO 和可用性目标由机构等级保护、数据量和基础设施共同确认；建议生产候选目标 RPO ≤ 15 分钟、RTO ≤ 60 分钟、月可用性 ≥ 99.9%。

### 7.4 发布门禁

- 代码评审、lint、类型检查、单元、合约、集成和 P0 E2E 全通过。
- 数据迁移具备前向/回滚脚本，并在预生产完整演练。
- 无严重/高危安全问题；中危有负责人和截止日期。
- 性能无超过预算的回退；关键接口 SLO 仪表盘和告警已配置。
- 备份恢复、权限复核、审计抽查和回退演练通过。
- 产品、业务、数据、安全、运维共同签署 UAT。

## 9. 需要业务方确认的决策

- 第一目标是内部演示、单机构试点还是直接生产；本计划按“单机构生产试点”估算。
- 用户体系与机构 IdP（OIDC/SAML/LDAP）以及角色/数据范围模型。
- 首期数据源、日增量、历史数据量、敏感字段和数据驻留要求。
- 首批必须上线的场景及每个场景的业务准确率阈值。
- 私有化部署形态、基础设施约束、等保/审计要求和目标 SLO/RTO/RPO。
- Supabase/PostgreSQL 是否允许保留为元数据库；若不允许，替换为机构标准 PostgreSQL 服务。
